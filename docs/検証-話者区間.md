# 検証: ASR の区間の内側で話者を判定する

他人を「自分」と誤る率を減らす方法を、JVS の合成会話で比べた記録。**数値はすべて参考値。** 読み上げ音声をつないだ合成会話で、Mac で計算した。実際の会話でも Pixel でも測っていない。アプリのコードは変えていない。

## 推薦

**ASR の区間はそのままにして、区間の内側で 1.5 秒の窓を 0.75 秒ずつずらして embedding を取り、ヒステリシスで平滑化する。文字起こしは ASR のトークンの時刻で話者ごとに分ける。**

| 項目 | 値 |
|---|---|
| 窓 | 1.5 秒、ずらし 0.75 秒。区間が 1.5 秒以下なら全体で 1 つ |
| ヒステリシス | 類似度 0.60 以上で自分に入り、0.55 未満で出る |
| 不明の帯 | 同じ判定が続くまとまりの平均類似度が 0.45〜0.60 なら不明。入れるほうを勧める(後述) |
| 文字起こしの割り当て | トークンの時刻で分ける。多数決にしない |

値は開発用の 10 本で決めた。しきい値は下の感度の表のとおり動きやすいので、端末で調整する前提は変わらない。

しきい値はこの推薦のまま実機に持ち込むと自分を他人としやすかったので、後ろの「実機に寄せた条件の測定」で下げた。窓の判定の推薦は変わらない。

現状との比較(不明の帯なし。評価用 20 本 / 確認用 30 本)。

| 条件 | 現状: 再現率 | 現状: 誤受入 | 推薦: 再現率 | 推薦: 誤受入 |
|---|---|---|---|---|
| clean | 96.8 / 96.4% | 31.1 / 22.6% | 97.8 / 98.3% | **0.3 / 0.5%** |
| SNR 15 dB | 84.0 / 90.7% | 24.2 / 20.9% | 87.6 / 89.4% | **0.1 / 0.3%** |
| 間を詰めた会話 clean | 89.5 / 92.0% | 66.8 / 60.4% | 95.4 / 94.8% | **2.8 / 1.5%** |
| 間を詰めた会話 SNR 15 dB | 77.8 / 83.6% | 57.1 / 52.4% | 85.1 / 87.6% | **0.9 / 0.8%** |

再現率はほぼ下がらず(確認用の SNR 15 dB だけ 1.3 ポイント低いが、95% 区間は重なる)、誤受入は 1〜2 桁下がった。代わりに embedding の計算は約 2.1 倍になる。Mac の 1 スレッドの実時間比で 0.0051 から 0.0109。常時ではなく発話の後にだけ動く。

電池が足りない場合の代わりは **エネルギーの谷で分ける案(B1 d10)** で、しきい値は 0.6、1.5 秒未満の部分は類似度に 0.1 を足す。計算量は現状とほぼ同じ(0.0054)。誤受入は推薦より高い(clean 2.2 / 0.8%、間を詰めた clean 5.9 / 3.2%)が、現状よりはるかに低い。雑音下の再現率は推薦より約 6 ポイント低い。

**判断が要る点が 1 つある。** 時刻で分けると、ASR の 1 区間から話者の違う複数の文字列ができる。今の `utterance` は 1 行 1 話者なので、行を分けるか、行の中に話者の範囲を持つかを決める必要がある。多数決なら形は変わらないが、下の表のとおり再現率が大きく落ちる。

## 分かったこと

- **主因は embedding の精度ではなく区間の取り方だった。** 窓の embedding を区間ごとの多数決に戻すと、clean で再現率 73.6%、誤受入 6.0% になる。以前の窓ずらしの 71.4%、4.4% に近い。以前の再現率の低さは、窓にしたことではなく、区間全体を 1 つの判定にまとめたことから来ていた
- **文字起こしは時刻で分ける。** 同じ判定でも多数決にすると、すべての案で悪化した(下の表の B1 と B2'、D2 と D2')。間を詰めた会話の再現率は 24〜55% まで落ちる
- **文字単位でも時間単位と同じ結果になった。** 推薦の clean で、他人の文字を自分とした率は 0.3%、自分とした文字のうち本当に自分の文字は 99.4%。現状は 29.0%、66.5%
- **短い無音の区切りは、間の長い会話でだけ効く。** VAD の無音 0.2 秒(B1 s20)は clean の誤受入が 0.0% だが、間を詰めると 14.0%、雑音を足すと 28.6%。SNR 15 dB では VAD が区間を切らなくなる。s20 の部分の平均は clean 1.65 秒、SNR 15 dB 3.93 秒、間を詰めた SNR 15 dB 7.2 秒
- **エネルギーの谷は雑音に強い。** 区間の下位 10% + 10 dB を 0.12 秒以上下回る谷で切ると、2 人が入る部分は SNR 15 dB で 0.1%、間を詰めた SNR 15 dB でも 1.6%(s20 は 6.1%、35.2%)
- **変化点の検出は DER が最もよいが、間が詰まると弱い。** C1 w15h05 は DER が最も低い(clean 16.7%)。誤受入は間を詰めた clean で 8.8% と推薦の約 3 倍で、窓をまたいだ判定が残る
- **ヒステリシスと多数決の平滑化の差は小さい。** 多数決(D1)は誤受入を少し下げるが、雑音下の再現率が約 6 ポイント低い
- **2 段のしきい値は、自分の取り違えではなく「自分を他人とする」誤りを減らす。** 推薦に不明の帯を足すと、誤受入はほぼ同じで、自分を他人とする率は clean 2.1→0.7%、SNR 15 dB 12.4→5.4% に下がる。不明は発話時間の 2〜10%。帯の上を 0.60 より上げると、誤受入は減るが再現率が大きく落ちた(d10 の帯 0.55〜0.65 は SNR 15 dB の再現率 67.9%)
- ToDo 抽出が不明の発話をどう扱うかで、不明の帯の価値が変わる。自分のものとして扱わないなら、取り違えを増やさず帯を入れられる。ただし DER は上がる(clean 24.5→31.4%)。不明を未割り当てとして数えるため

### 検証の前提で分かったこと

**今の合成会話は、話者交代の間が短くない。** 以前の記録は「発話の間が短い」と書いていたが、話者交代の無音は中央値 1.24 秒で、0.2 秒未満は 0.3%、0.8 秒未満も 7.9% だった。JVS の音声の前後に無音が入っているため。それでも 25% の区間に 2 人が入るのは、実際の無音が 0.8 秒より長くても VAD が切らないことがあるため。たとえば音素のラベルで 1.09 秒の無音が切れなかった例がある。VAD の確率が発話の後すぐに下がらないためと考えられるが、確かめていない。

実際の会話の交代はもっと短いと考えられ、この会話だけでは無音で切る案が過大評価になる。そのため、発話の前後の無音を切り詰め、間を平均 0.15 秒にした会話(以下「間を詰めた会話」)を足した。交代の無音は中央値 0.19 秒で、2 人以上が入る区間は 79%(SNR 15 dB は 88%)。分布は実測ではなく負荷試験で、値は決めの材料にとどめる。

### 計算量

| 案 | embedding 回/分 | 計算する音声 秒/秒 | CPU 実時間比 | 現状との比 |
|---|---|---|---|---|
| 現状 | 7 | 0.98 | 0.0051 | 1 |
| B1 d10 | 28(SNR 15 dB は 44) | 0.87 | 0.0054(0.0061) | 1.1(1.2) |
| D2 窓 1.5 / 0.75 | 67 | 1.67 | 0.0109(0.0116) | 2.1(2.3) |
| D2 窓 1.5 / 0.5 | 95 | 2.37 | 0.0155 | 3.0 |
| C1 変化点 1.5 / 0.5 | 95 | 2.37 | 0.0155 | 3.0 |

- 値は `0.0024 + 0.00493 × 音声の秒` の近似で計算した。Mac の 1 スレッド、CPU 時間で実測してあてはめた。この会話はほとんどの時間に発話があるので、発話の少ない実際の 1 日の平均ではない
- 比べる相手として、ASR の実時間比は 0.012、VAD は 0.0025(常時)。推薦の増分 0.0058 は、発話中の処理(VAD、ASR、embedding)の合計 0.0254 の約 2 割にあたる
- 1 区間 20 秒の上限でも、embedding は 25 回程度で、発話の終了後に Mac で 0.25 秒ほど。実時間で動く
- 追加の VAD は要らない。`UtteranceSegmenter` はフレームごとの判定を受け取っている。無音の案も部分の境界は同じ判定から取れる。VAD のしきい値 0.7 の案だけは 2 つ目の判定が要る
- エネルギーの谷は 20 ms ごとのエネルギーだけで、計算は無視できる

## 感度

推薦のしきい値(入る / 出る)をずらした値。評価用 20 本。

| しきい値 | clean 再現率 / 誤受入 % | SNR 15 dB 再現率 / 誤受入 % | 間を詰めた clean | 間を詰めた SNR 15 dB |
|---|---|---|---|---|
| 0.50 / 0.45 | 99.7 / 11.7 | 97.6 / 5.4 | 98.2 / 16.9 | 95.5 / 7.9 |
| 0.55 / 0.50 | 99.3 / 3.9 | 95.0 / 1.0 | 97.2 / 8.2 | 92.4 / 2.5 |
| **0.60 / 0.55** | 97.8 / 0.3 | 87.6 / 0.1 | 95.4 / 2.8 | 85.1 / 0.9 |
| 0.65 / 0.60 | 94.3 / 0.1 | 71.9 / 0.0 | 91.9 / 1.0 | 69.6 / 0.2 |
| 0.70 / 0.65 | 84.6 / 0.0 | 47.3 / 0.0 | 80.4 / 0.4 | 42.7 / 0.1 |

0.05 の違いで誤受入も再現率も大きく動く。雑音の環境でも差がある。SNR 15 dB の再現率(評価用と確認用)は TCAR 97.8%、DWASHING 98.6% に対し、PRESTO 70.1%、DKITCHEN 77.2%、PCAFETER 77.7%。会話ごとの最低は 47.5%。登録は静かな音声のままなので、人の声や食器の音が重なる場所では自分の類似度が下がる。

## 計測条件

| 項目 | 内容 |
|---|---|
| 音声 | `der_eval.py` の合成会話。180 秒前後、2〜4 人、10% は発話が重なる。自分は 0 番目の話者 |
| 登録 | parallel100 の 3 発話の平均。アプリと同じ数。SNR 15 dB でも登録は clean |
| 雑音 | DEMAND の 12 環境。会話ごとに 1 環境 |
| 区間 | `silero_vad.onnx`、しきい値 0.5、無音 0.8 秒、最大 20 秒。前に 0.3 秒足す。ASR の区間はどの案も同じ |
| embedding | CAM++ advanced、1 スレッド。現状は以前と同じく後ろに 0.8 秒足す。案は発話の部分だけ |
| ASR | zipformer-reazon の int8。区間の前後に実音声と無音を 0.3 秒ずつ足し、トークンの開始時刻を使う |
| 開発用 | 会話 0〜9。clean で再現率 90% 以上、SNR 15 dB で 80% 以上の中から、2 条件の平均の誤受入が最小の設定を選ぶ。条件ごとに別の値は使わない(端末は SNR を知らない) |
| 不明の帯 | 開発用の 4 条件で、不明が 10% 以内で、誤受入 × 3 + 自分→他人 が最小の帯を選ぶ。3 倍は仮の重み。帯の上下は 0.05 刻み |
| 評価用 | 会話 10〜29。以前の 30 本に含まれる |
| 確認用 | 会話 30〜59。開発用の話者を除いて作り直した |
| 計測機 | Apple M5、macOS 26.6.2、sherpa-onnx 2.0.1、Python 3.12.16 |

以前の値が再現できることを確かめた。30 本全体の現状は clean 95.0 / 30.9%、SNR 15 dB 85.7 / 28.2%、2 人が入る区間は 24.9%(175/704 と同じ)、37.7%。再現率の 0.1 ポイントの差は時間の丸めによる。

- 時間の数え方は `der_eval.py` の `self_other_accuracy` と同じ。正解は音素のラベルで、重なりは自分がいれば自分とする
- 短い部分(0.4 秒未満)は embedding を取らず、隣の長い部分に吸収する
- 以前の DER(無音 0.2 秒で 12.4%)とは比べられない。VAD の版、登録の数、しきい値が違い、この表は短い部分の仮の話者の扱いも違う。DER の誤検出の約 12%(clean)は、0.2 秒の VAD の部分に含まれる語間の無音で、案の差ではない
- 評価用の表を見て推薦を選んだので、評価用の値には選択の影響が少し入る。確認用の値はその影響を受けない
- 計算中は別の検証が動いていて、ロードアベレージは 2〜32 だった。CPU 時間は別に測った値を使っているが、完全な無負荷ではない

JVS は再配布できないのでコミットしない。音声は保存せず、`embedding` と ASR の結果は `.cache/speaker_seg/` に置いた。コミットした JSON には集計値だけが入っている。

## 未検証

- 実際の会話。JVS は読み上げで、相づち、言いよどみ、笑い、重なりが少ない。間を詰めた会話も切り貼りで、交代の分布は実測ではない
- 端末のマイク、ポケットの中、離れた話者。登録と試験は同じ収録環境
- 同じ人の体調や話し方の変化、声の似た家族
- 短い発話での判定。JVS は 1 発話が数秒あり、1 秒未満の相づちはほとんどない
- Pixel での速度、メモリ、電池、発熱
- Android の AAR でトークンの時刻が取れること。Python の sherpa-onnx では取れた。トークンの時刻の精度は単独では確かめておらず、文字単位の指標が時間の指標と揃うことだけを見た
- `tools/eval` の Kotlin での再現
- 推薦と C1 の組み合わせ。窓の判定に変化点を足すと DER が下がる可能性がある
- 区間全体の embedding で明らかに他人の区間は窓を省く案。電池を減らせる可能性があるが、測っていない
- 端末でのしきい値の調整方法。別の話者の集団で決めた値は持ち越しにくい
- 雑音の除去(`OfflineSpeechDenoiser`)の前処理
- 3 倍の重みが ToDo 抽出の害を正しく表しているか。ToDo の評価では測っていない

## 再現の手順

`tools/spike-asr/` で実行する。先に `docs/検証-ASR.md` の `fetch.py` でデータとモデルを用意する。

```bash
mise exec -- uv run python speaker_seg_data.py --conds clean,snr15,tclean,tsnr15 --start 0 --end 60 --jobs 7
mise exec -- uv run python speaker_seg_data.py --conds clean,snr15,tclean,tsnr15 --start 0 --end 60 --jobs 7 --asr
mise exec -- uv run python speaker_seg_data.py --timing
mise exec -- uv run python speaker_seg_eval.py stats
mise exec -- uv run python speaker_seg_eval.py sweep
mise exec -- uv run python speaker_seg_eval.py report --c0 0.0024 --c1 0.00493
```

## 実機に寄せた条件の測定

Pixel の Release で長時間の文字起こしをすると、2 人の会話でも話者が増え続け、自分を他人と判定することがあった。実機の音声は使えないので、登録と試験の条件を変えた合成の会話で原因と対策を確かめた。**実機の代わりではなく、値はすべて仮。** 上の推薦と同じ窓の判定を使い、しきい値、仮の話者の扱い、自分の声の更新だけを変えた。

### 結論

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 自分に入る / 出る / 不明の下端 | 0.60 / 0.55 / 0.45 | 0.50 / 0.45 / 0.40 |
| 既存の話者との類似度 | 0.60 | 0.45 |
| 仮の話者の上限 | なし | 3 |
| 新しい話者を作るまとまりの長さ | 1 秒 | 2 秒 |
| 重心の重み | 発話の回数 | 発話の長さ |
| 知っている他人との比較 | なし | 不明の帯は差 0.05、弱い自分の判定は差 0.10 |
| 自分の声の更新 | なし | 登録は変えず、類似度を最大 0.05 上げる |

評価用 20 本の `mixed`(机の上、ポケット、人の声のある場所を聞き取りごとに変える)の値。

| 規則 | 再現率 % | 誤受入 % | 不明 % | 話者数 平均(最大) |
|---|---|---|---|---|
| main | 61.8 | 0.7 | 12.3 | 9.1(15) |
| 推奨 | **85.0** | **3.1** | 1.0 | **2.2(3)** |

95% 区間は再現率 75.6〜92.2、誤受入 2.1〜4.1(main は 52.9〜69.6、0.4〜1.0)。**代わりに誤受入は約 4 倍になる。** 他人の取り違えは ToDo の害が大きいが、再現率の低さが実機の問題なので受け入れた。本物の話者は 1.33 人(他人の平均)なので、話者数は 2.2 でもまだ多い。

### 分かったこと

- **報告の症状は合成でも再現した。** main の規則で話者は聞き取りを重ねるごとに 2.8、4.3、7.3、9.1 人と増え、最大 15 人。再現率は `cafe` で 32.1%
- **増えた話者の多くは他人ではなく自分の声だった。** 話者のまとまりのうち、自分の時間が他人の時間より長いものが 1 会話あたり平均 2.85 個あった。しきい値 0.6 では端末の条件で下がった自分の声が「他人」になり、窓の短い特徴量のばらつきで新しい話者になる
- **上限だけでは足りない。** main に上限を足すと話者は 3 人に収まるが、再現率は変わらない
- **仮の話者のしきい値より、作るまとまりの長さが効く。** 上限なしで 1 秒のままだと 0.45 でも 4.6 人だが、2 秒にすると 2.0 人(開発用 `mixed`)
- **しきい値を緩めるだけだと誤受入が増える。** 0.50 で比較なしは再現率 87.6%、誤受入 4.4%、不明 6.8%。知っている他人と比べると、誤受入 2.2%、不明 1.1% に下がるが、再現率も 79.9% に下がる。自分の声が仮の話者に入っていると、その話者に負けるため
- **自分の声の更新は再現率を上げるが、そのままでは誤受入も上げる。** 上限なしは再現率 89.1%、誤受入 4.7%、`pocket` の誤受入は 17.9%。育てた声が部屋や端末の癖も学び、同じ場所の他人も上がると考えられるが、確かめていない。上げ幅を 0.05 に抑えると、再現率 85.0%、誤受入 3.1% になった
- **登録の場所は大きく効く。** 聞き取りと同じ机の上で登録すると `mixed` の再現率は 91.3%、誤受入は 6.8%。`studio` の再現率は 80.2% に下がる。画面の登録のやり直しの案内はこの結果に合わせた
- **登録の形の差は小さい。** 区間全体の平均を 1.5 秒の窓の平均にしても、開発用の `mixed` の再現率は 89.6 → 90.6%。条件によっては下がるので変えなかった。外れた 1 発話を落とす案は再現率が 84.7% に下がった
- **音源は揃っていた。** 登録も聞き取りも `microphoneAudioSource()` で `VOICE_RECOGNITION` を開く。端末の中の処理(AGC など)は確かめていない
- 重心の重みを長さにした差は小さい。再現率 83.6 → 85.0%、誤受入 2.9 → 3.1%。区間は重なり、効いたとは言えない
- 重心に自分と近い話者を比較から外す案(開発用)は誤受入が増えたので入れなかった

### 既存の話者のまとめ直し

`mixed` の評価用 20 本で、前半 2 回を main の規則で聞き取り、まとめ直してから、後半 2 回を推奨の規則で聞き取った。

| 項目 | 値 |
|---|---|
| まとめ直しの前の話者数 | 平均 4.3(最大 9) |
| まとめ直しの後 | 平均 2.1 |
| 後半の話者数 | 平均 2.6(最大 3) |
| 後半の再現率 / 誤受入 | 75.3 / 2.1%(95% 区間 62.7〜86.1 / 1.4〜3.0) |

最初から推奨で聞き取るより再現率が約 10 ポイント低い。まとめた話者に自分の声が残り(平均 0.55 個)、比較で負けるため。自分の声が入った話者は手で「自分」へ統合すると解消する。自動では統合しない。

### 計測条件

| 項目 | 内容 |
|---|---|
| 会話 | 5 分の聞き取りを 4 回、計 20 分。聞き取りをまたいで話者と重心を持ち越す。3 で割って 2 余る番号は 3 人、残りは 2 人 |
| 発話 | JVS。相づち(0.4〜0.9 秒)3 割、短い発話(1〜2.5 秒)4 割、残りは 1 文。音素の境界で切り貼りしたので、自然な発話ではない |
| 登録 | 全条件で口元、静か(残響 0.2 秒、DRR +12 dB、SNR 30 dB)。parallel100 の 3 発話を最長 6 秒で |
| `studio` | JVS のまま |
| `table` | 残響 0.35 秒、DRR 自分 +3 / 相手 -2 dB、相手は 4 dB 小さい、静かな雑音 SNR 20 dB |
| `pocket` | 残響 0.25 秒、2.5 kHz の低域通過、相手は 5 dB 小さい、SNR 12 dB |
| `cafe` | 残響 0.55 秒、人の声や食器の雑音 SNR 8 dB、0.5 秒の時定数の簡単な AGC |
| `mixed` | 聞き取りごとに table、pocket、cafe、table |
| 共通 | 120 Hz の高域通過。残響は合成。端末のマイクの測定値ではない |
| 区間 | `silero_vad.onnx`、0.5、無音 0.8 秒、最大 20 秒、前に 0.3 秒 |
| 開発用 | 会話 0〜9。話者 30 人から。しきい値と規則を決めた |
| 評価用 | 会話 10〜29。残りの 70 人から。話者は開発用と重ならない |
| 計測機 | Apple M5、sherpa-onnx 2.0.1、1 スレッド |

開発用より評価用のほうが再現率が低い(`mixed` 94.9 → 85.0%)。話者の違いが大きく、開発用の値は楽観的と考える。

一度評価用を見た後で、弱い自分の判定を変える差を 0.05 から 0.10 に変えた。値は開発用で選んだが、評価用の値に選択の影響が少し入る。変更前の推奨は再現率 80.3%、誤受入 2.7%。

Kotlin の規則との違い:

- `speaker_field_eval.py` は `SpeakerIdentifier` と `voiceRuns` を Python に移したもの。同じ入力で両方を流して比べてはいない
- トークンの時刻がない。本文のないまとまりを落とす処理と、本文の境界への丸めを再現しない
- 長く更新のない話者が席を譲る処理は再現しない。測定は 20 分で、7 日に届かない
- 語頭のバッファは PRE の 0.3 秒で代用する(話者区間の検証と同じ)
- 音素のラベルの有声区間を正解にする。短い発話の間の無音は時間に数えない

### 未検証

- Pixel での値。合成の残響、帯域制限、AGC が実機に近いかは分からない。「話者」の画面の判定の記録で確かめる
- 自分の声の更新の長期の動き。20 分の測定で、誤学習が積み重なるかは見ていない
- 同じ条件が続いたときの自分の声と部屋の癖の分離
- 3 人を超える会話、テレビや動画の音声。周りの声が上限の席を埋める場合
- 声の似た家族。性別の組み合わせで分けていない
- 手の修正の効果。テストで重心が動くことは確かめたが、判定がどれだけよくなるかは測っていない
- Pixel での計算量。更新で判定ごとの DB の読み書きが少し増える

### 再現の手順

`tools/spike-asr/` で実行する。`.cache/` のデータ、雑音、話者のモデル、VAD は上の手順と同じ。音声は保存せず、窓の embedding を `.cache/speaker_field/` に置く。コミットした JSON には集計値だけが入っている。

```bash
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_data.py --conds studio,table,pocket,cafe,mixed --start 0 --end 30 --jobs 8
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py self
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py provisional
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py enroll
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py adapt
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py rival
OMP_NUM_THREADS=1 mise exec -- uv run python speaker_field_eval.py report
```

`results/speaker_field/comparison.json` に、開発用、評価用、感度、まとめ直しの値がある。
