# 検証: ローカル LLM

端末で動かせるサイズの LLM を、架空の日本語会話で比べた記録。実施は 2026-10-31〜11-01、環境は Apple M5(RAM 32GB)の Mac。**Pixel では計測していない。**

スクリプト、評価セット、生の出力は [tools/spike-llm/](../tools/spike-llm/) にある。

## 推薦

**第一候補は Gemma 4 E4B を LiteRT-LM の GPU で動かす構成。**

| 項目 | 推薦 |
|---|---|
| 要約、ToDo、質問応答 | Gemma 4 E4B、思考モードなし。JSON は制約デコードを使わず、自由形式で出して検証する |
| 話者名の推定 | 同じモデルで思考モードあり |
| 検索 | EmbeddingGemma 2 Text 270M。文字列の完全一致の検索を併用する |
| 次善 | Gemma 4 E2B。品質は落ちるが、Tensor G6 の NPU 向けファイルがある |

理由:

- ToDo の抽出、要約、質問応答のすべてで最も成績が良かった。ToDo は適合率 0.98、再現率 0.91で、次点との F1 の差は 0.14
- 日本語向けの LFM2.5-JP は、期待に反して抽出と指示の順守が弱かった。「日本語に強い小型モデル」が今回のタスクに強いとは限らない
- ライセンスは Apache-2.0
- 充電中のバッチなら、速度の差は問題になりにくい

注意点:

- **LiteRT-LM の制約デコードは、今の Gemma 4 には使えない。** E4B では全件が空の出力になった(下の「分かったこと」を参照)
- E4B の、Tensor G6 向けの NPU ファイルは公開されていない(取得時のリビジョン)。Pixel では GPU か CPU で動かす前提になる
- ファイルサイズは 3.66GB と候補の中で最も大きい。GPU 専用の `gemma-4-E4B-it-gpu.litertlm` は 2.97GB で、こちらは測っていない
- データは 30 会話と小さい。再現率 0.91 は 41/45 件で、95% 信頼区間はおよそ 0.79〜0.96(Wilson)

### LFM と Qwen を llama.cpp で動かした理由

依頼の条件は「LiteRT-LM を優先し、Mac で動かない場合に代用する」だった。LiteRT-LM は Mac で動いたが、次の理由で LFM と Qwen は llama.cpp に切り替えた。**依頼の条件とは別の理由での代用**である。

- `litert-community` の LFM と Qwen の `.litertlm` は、コミット履歴を見ると個人の変換者によるもので、モデルの提供元の配布物ではなかった。組織は Hugging Face の認証がなく、メンバーは 2,821 人いる
- 「信頼できる公式の配布元からだけ取得する」条件を優先し、これらは取得しなかった。提供元が公開している GGUF を使った
- Gemma 4 と EmbeddingGemma 2 の `litert-community` 版は、Google の関係者と見られるアカウントのコミットで、E4B は LiteRT-LM の公式 README が案内している。E2B と EmbeddingGemma 2 は README での言及までは確認しておらず、同じアップロード元であることからの判断

このため、LFM と Qwen の成績は LiteRT-LM での成績ではない。下の対照実験が示すとおり、基盤や量子化が変わると結果も変わる。

## 評価の方法

- 評価セット: 架空の会話 30 件(`tools/spike-llm/data/eval.yaml`)。ToDo の正解 45 件と任意の 9 件、質問 67 問(うち回答不能 8 問)、話者 39 人(うち名前が不明 13 人)。別に調整用の 2 件がある
- 混ぜた難所: ASR の誤り 12 件、話者ラベルの誤り 5 件、他人の作業 14 件、取り消し 5 件、仮定や願望 4 件、ToDo なし 4 件、第三者の名前 10 件、完了済み 2 件
- 採点: 正解の語句との部分一致で機械的に採点する(`scripts/score.py`)。任意の正解に当たった予測は、正解にも誤検出にも数えない
- 要約: 機械採点(事実の網羅率)に加えて、モデル名を隠した盲検で 1〜5 点を付けた。採点者は Claude で、1 回だけの採点
- 質問応答: 正解の会話に無関係な会話を 2 件混ぜて渡し、検索の上位に別の会話が混ざる状況を再現した
- 生成の設定: 温度 0、top_k 1、文脈長 4096 トークン
- プロンプトは調整用の 2 件だけで調整し、評価セットを流す前に固定した

### 速度とメモリ

速度は Mac の値で、Pixel の性能を示さない。他の作業と同居した状態(負荷平均 11〜30)で測った。特に CPU の値は負荷の影響が大きい。

| モデル | サイズ | GPU 生成 tok/s | GPU 入力 tok/s | CPU 生成 tok/s | ピーク footprint(CPU) | ピーク RSS(CPU) |
|---|---:|---:|---:|---:|---:|---:|
| E4B | 3.66GB | 29.4 | 360 | 1.9 | 1.80GB | 3.40GB |
| E2B | 2.59GB | 54.8 | 1,209 | 6.5 | 1.38GB | 2.64GB |
| LFM-JP | 1.25GB | 47.2 | 2,150 | 14.3 | 1.50GB | 2.77GB |
| Qwen3 | 2.50GB | 24.6 | 556 | 7.6 | 4.01GB | 6.56GB |
| E2B-GGUF | 3.35GB | 37.7 | 989 | 19.4 | 1.85GB | 5.28GB |

- 速度は 8 件の平均。CPU は 4 スレッド、GPU は Metal
- メモリの値は実行の規模が揃っていない。E2B は全 213 件、E4B は 12 件、他は 8 件の値。文脈長はすべて 4096
- RSS にはメモリマップしたファイルの分が含まれる。footprint はそれを含まない
- GPU のメモリは信頼できないので表に入れなかった。Mac の GPU が使う分を、この計測では正しく拾えていないと考えられる(例: Qwen3 の全件の実行の footprint は 10.72GB、8 件では 1.51GB と大きくずれた)
- 品質の評価は GPU で流した。E2B を全件の評価で 1 件あたり平均 4.7 秒、E4B は 7.4 秒、E4B の思考ありは 32 秒。いずれも他の評価と並列で動かした値

| 文字起こし | 埋め込み 256 次元 | 0.87 | 0.93 | 1.00 |

- 言い換えに強く、BM25 では見つからないものが見つかる

## 分かったこと

### LiteRT-LM の制約デコードが Gemma 4 で機能しない

`ResponseFormat.json(schema)` を指定すると、出力の形式は守られるが、中身が空に偏る。

- E4B: GPU は 30 件すべて、CPU は確かめた 11 件すべてが `{"items":[]}`。話者もほとんどが空で、思考モードありでも変わらなかった
- E2B: GPU は 9/30 件が空。CPU は再現率が 0.36 まで落ちた
- 同じ E2B を llama.cpp の JSON スキーマで制約すると、自由形式と同等の結果だった。モデルではなく、LiteRT-LM の制約デコードとの組み合わせの問題と考えられる。原因までは調べていない

自由形式でも E4B は JSON を 100% 正しく出せたので、制約デコードに頼らなくてよい。

### プロンプトの要点

全文は `tools/spike-llm/scripts/prompts.py` にある。

- **日付の表を渡す。** 今日からの 22 日分の日付と曜日を渡し、そこから選ばせる。調整用の会話で、モデルが曜日の暗算を誤ったので足した。表があっても誤りは残り、評価セットで表の有無を比べてはいない
- **やることの逆も書く。** 他人の作業、完了済み、取り消し、願望を「抽出しないもの」として並べる
- **具体例は架空の中身で 1 つ書く。** 形式だけの雛形を見せると、LFM が雛形の文言をそのまま写した
- **呼びかけの規則を明記する。** 「呼びかけられた名前は、話した本人ではなく、次に答えた話者の名前」
- **`evidence` を `name` の前に置く。** 根拠を先に書かせる
- **`system` に文字起こしの性質を書く。** 誤変換、言いよどみ、話者ラベルの誤りがあることと、「自分」が持ち主であること
- **出力の検証を `domain` に置く。** JSON の解析、日付の形式の確認、失敗時の再試行はコードで行う。E4B の思考ありでは、JSON の失敗が 1 件あった

### Gemma の thinking

E4B の thinking を使うなら、話者名の推定に絞るのが費用対効果が良い。

- 話者名は全体で 0.49 から 0.79 に上がった
- 要約の盲検は 3.97 から 4.20 に、質問応答は 0.97 から 1.00 に上がったが、件数からは小さな差
- ToDo の抽出は上がらなかった
- 1 件あたりの時間はおよそ 4 倍(並列実行時の値)

Android の Kotlin API にも `ThinkingConfig` がある。`thinkingTokenBudget` で上限を決められる。

## Mac と Pixel で差が出そうな点

- **品質が同じとは限らない。** 温度 0 でも、E2B の CPU と GPU で結果が違った(自由形式の適合率 0.76 と 0.70、制約デコードの再現率 0.36 と 0.60)。Pixel の GPU での再評価が必要
- **NPU 版は別のファイル。** Tensor G6 向けの E2B はファイルも違う(3.31GB)。文脈長はコンパイル時に固定される。GPU 版と品質が同じかは未確認
- **GPU の経路が違う。** Mac は Metal、Android は OpenCL。AndroidManifest に `libOpenCL.so` と `libvndksupport.so` の宣言が要る
- **メモリの測り方が違う。** モデルカードも、Android は RSS、Mac は footprint と分けている。12GB の端末でモデルカードの値の範囲に収まるかは、実機で測るしかない
- **発熱と速度の低下。** Mac の値からは分からない。長いバッチで温度による速度低下が起きるかは未確認
- **モデルの配置。** 3.66GB のファイルの置き場所、初回の読み込み時間、`cacheDir` の効果は未確認
- **Android の制約デコード。** Kotlin のソースに `ResponseFormat` はあるが、実行はしていない。Python と同じ問題が出ると見ておく
- **思考の出力。** Android では `channels["thought"]` で返る。本文の解析に混ざらないようにする
- **AICore。** モデルカードには、対応する Android 端末では Gemini Nano として Gemma 4 を AICore から使う経路が案内されている。今回は調べていない

## 測っていないこと

- Pixel での速度、メモリ、電池、発熱のすべて
- LiteRT-LM での LFM と Qwen(公式の配布物がない)
- E4B の GPU 専用ファイル(2.97GB)と、E2B の GPU 専用ファイル(2.01GB)
- Tensor G6 の NPU での動作
- 長い文字起こし。評価セットの最長は 818 文字。何時間分もの会話を、どう区切ればよいかは分からない
- E2B の思考あり、自由形式の ToDo と話者名
- Qwen3 の思考あり。1 件に約 85 秒かかり、完走に 3 時間以上の見込みだったので、8 会話で打ち切った。比較表には入れていない(途中の結果は `results/raw/qwen3-4b-think.gpu.test.jsonl`)
- 本物の ASR の出力。今回の誤りは手で作ったもので、実際の傾向とは違う可能性がある

## 評価の限界

- 評価セットとプロンプトと正解を、同じ作成者(Claude)が作った。自分で作った難所に寄っている可能性がある
- 部分一致の採点は表記の揺れに弱い。正解を広めに書いたので、緩めの採点になっている
- 調整用の会話は 2 件だけで、プロンプトは全モデルに合わせ切れていない。LFM は別のプロンプトならもっと伸びる可能性がある
- E4B と E2B-GGUF では量子化の方式が違う。今回の差のうち、モデル、量子化、基盤のどれが効いたかは切り分けていない

## 再現の手順

```bash
cd tools/spike-llm
mise install
mise exec -- uv sync
mise exec -- .venv/bin/python scripts/fetch_models.py
mise exec -- bash scripts/run_all.sh /tmp      # 品質の評価
mise exec -- bash scripts/run_speed.sh         # 速度
mise exec -- .venv/bin/python scripts/score.py
```
