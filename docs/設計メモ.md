# 設計メモ

決まったことと、その理由を残す。

## 決定事項

| 項目 | 決定 | 理由、補足 |
|---|---|---|
| 想定端末 | Pixel 11 | RAM は 12GB を基準にする |
| 音声の保存 | 残さない | 処理中のバッファだけをメモリに持ち、文字起こし後に捨てる |
| 話者の表記 | 「自分」と「それ以外」から始める | 会話の流れで名前が分かれば更新する |
| 聞き取りの停止 | 手動 | ローカルでだけ使う前提なので、自動停止は作らない |
| 再起動後 | 通知で起動を促す | 下の「再起動後の流れ」を参照 |
| 電池の目標 | 1日で 20% 以内(仮) | 実測してから見直す |
| ネットワーク | 開発中はモデルの取得に使う | 利用者の操作でアプリが取得する。Release も INTERNET 権限を持つ。モデルが確定したら、取得のコードと権限を外す |
| 検証データ | 公開データを使う | 自分の録音を待たずに進める |

## アーキテクチャ

録音、文字起こし、整理、リマインドはアプリを閉じていても動く。LLM はメモリを大量に使うので、管理する場所を1か所に絞る。そのため、ビジネスロジックは Kotlin のエンジンに置き、React Native は画面だけを担当する。

| 役割 | 実体 |
|---|---|
| エンジン | Foreground Service、WorkManager の上で動く Kotlin |
| 境界 | Expo Module(`modules/engine-bridge`)。小さく保つ |
| 画面 | React Native |
| DB | SQLite。書き込むのはエンジンだけ |

- `engine/domain` は Android プラグインのない純粋な Kotlin モジュールにする。Android の API を呼ぶとコンパイルが通らない
- `domain` は `AudioSource`、`Transcriber`、`Llm`、`MemoRepository`、`Clock` などのインターフェース越しに外部を使う
- `domain` の担当: 発話区間の扱い、話者のまとめ方、メモの区切り方、ToDo の抽出、リマインドの判定、プロンプトの組み立て、LLM の出力の解析
- `packages/engine-client` に Fake 実装を置き、エンジンなしで画面を開発できるようにする
- iOS を作るときは、`domain` を Kotlin Multiplatform に寄せることを検討する。今は作り込まない

## CI と配布

| いつ | どこで | 内容 |
|---|---|---|
| push / PR ごと | GitHub Actions | lint、型検査、Vitest、Kotlin の単体テストと結合テスト |
| ネイティブ周りの変更時、main へのマージ時 | GitHub Actions | Android の Debug ビルド |
| バージョンタグ | GitHub Actions | 署名済みの arm64 Release APK をビルドし、GitHub Releases に置く |
| 手動(`workflow_dispatch`) | GitHub Actions | 任意のブランチから APK をビルドする |
| モデルを変えるとき | 手元の Mac | 公開データでの精度評価。結果はコミット |
| 節目ごと | Pixel | 通しの動作確認、電池、発熱 |

- CI でも `mise-action` で `mise.toml` を読み、`mise run` のタスクを実行する
- Gradle と pnpm はキャッシュする
- 署名鍵は固定する。鍵が変わると上書きインストールできず、アンインストールすると端末内のメモも消える。鍵は GitHub Secrets と別の場所の両方に保管する
- `versionCode` はタグや実行番号から自動で付ける
- 開発版はアプリ ID を `.dev` 付きにして、普段使いの版と共存させる
- INTERNET 権限を外した後は、Release ビルドのマニフェストに権限がないことを CI で確かめる
- 解析 SDK など、禁止する依存関係が入っていないことを CI で確かめる
- Play 以外で配るアプリの開発者確認の動向に注意する。日本での開始時期は未確認

## 最初のゴール

発話を検知し、文字起こしを SQLite に保存して、一覧で見られるようにする。

話者識別、メモの整理、ToDo、質問応答はこの後で足す。

## 再起動後の流れ

マイクの Foreground Service は、バックグラウンドから開始できない。BOOT_COMPLETED の receiver からも開始できない。そのため次の流れにする。

1. BOOT_COMPLETED の receiver が通知を出す
2. 利用者が通知をタップしてアプリを開く
3. アプリが前面にある間に Foreground Service を開始する

通知を出すには POST_NOTIFICATIONS の許可が要る。この流れは実機で確かめる。

アプリを開いただけでは開始せず、画面のボタンで始める。

## 権限

INTERNET はモデルの取得のために Release にも残す。利用者は外出先からスマホだけで APK を入れて試すので、`adb` では入れられないため。`scripts/check-release-manifest.sh` は今は INTERNET があることを確かめる。モデルが確定したら、権限を外して、このスクリプトをないことの確認に戻す。

モデルの取得には `FOREGROUND_SERVICE_DATA_SYNC` と `WAKE_LOCK` も使う。取得のコードと一緒に外す。

`ACCESS_LOCAL_NETWORK` は `react-android` の debug の AAR が宣言する(Android 17 で Metro につなぐため)。release の AAR にはなく、Release のマニフェストには入らない。`mise run build:android:release` が `scripts/check-release-manifest.sh` で確かめる。

## 話者

音声は残さないが、話者を見分けるために、話者の特徴量(embedding)は端末内に残す。

- 自分の声は初回に登録する。登録の前は話者を判定しない
- それ以外の声は、特徴量のまとまりごとに仮の話者として扱う
- 会話の流れから LLM が名前を推定し、仮の話者の名前を更新する
- 名前は推定なので、手で直せるようにする

## 検証データ

| 目的 | データ | 注意 |
|---|---|---|
| 文字起こし | Common Voice の日本語 | 利用条件を取り込むときに確かめる |
| 話者識別 | JVS | 利用条件を取り込むときに確かめる |
| 複数人の会話 | JVS の発話をつないだ合成データ | 実際の会話とは違うので、参考値として扱う |
| 発話検知 | 上の音声に雑音や無音を混ぜた合成データ | 雑音の出どころも公開データにする |

- データ本体はコミットせず、取得スクリプトと評価の結果だけをコミットする
- ReazonSpeech は、利用目的に制限があるため後回しにする
