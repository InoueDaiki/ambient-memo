## Pixel での電池の測定

### 2026-11-04 聞き取りの有無(1 回目)

Pixel 11、アプリは `0.0.0-dev.13`。「記録」の書き出しから読んだ。電池の容量は満充電の値から約 4,870 mAh。残量は 5 分ごとに 2.5 mAh 刻みで読むので、5 分の区間の電流は 30 mA 刻みになる。

| | 聞き取りあり | 聞き取りなし |
|---|---|---|
| 時間 | 9:11〜14:19(5 時間 5 分) | 14:19〜18:32(4 時間 13 分) |
| 電池 | 100% → 81%(888 mAh) | 81% → 74%(355 mAh) |
| 平均の電流 | 約 174 mA(1 時間に約 3.6%) | 約 84 mA(1 時間に約 1.7%) |
| CPU が起きていた時間 | すべて(`uptimeMs` と `elapsedMs` が同じだけ進む) | 4 時間 16 分のうち 44 分 |

- 聞き取りなしの時間には、画面を使った時間も入っている。画面を消して置いた状態の値ではない
- 聞き取り中に画面が消えていて静かな間は、約 90 mA。CPU は 1 コアの約 2.5%。CPU がスリープしないことが主な原因と見ている。録音中は Android が端末をスリープさせないと見ているが、確かめていない
- 会話が続いた 13:00〜14:10 は、5 分のうち約 4 分が発話で、CPU は 1 コアの 15〜18%、電流は 120〜180 mA。文字起こしの時間は 5 分に約 11 秒なので、残りは話者の判定か VAD と見ている。記録ではこの 2 つを分けられない
- VAD を飛ばしたフレームは、静かな間は 40〜70%、会話や雑音が続いた間は 5〜15%
- 発話は 472 件(保存 428、雑音として除いた 44)。待ちは最大 2.3 秒で、古い発話を捨てたものはない
- メモリは会話の間に約 1 GB まで増え、静かになると約 130 MB に戻った
- 静かな間の約 90 mA だけでも、16 時間で約 30% になる。目標の「1 日で 20% 以内」には届かない

## 仮で決めたこと

あとで変えてよい判断を残す。

- ToDo の機能をなくした(利用者の指示)ので、既存の行も移行で消した。残す場所がないため
- 質問の検索はベクトルを使わず、LLM が考えた語で、タイトル、要約、発話を部分一致で探す。埋め込みのモデルを足さずに済むため。見つからなければ語を変えて 1 回だけ探し直す
- 質問のプロンプトは JSON にせず、行の形で答えさせる。読めなくても再試行しない
- 質問のモデルは質問のたびに読み込み、答えたら解放する。常駐させるとメモリを数 GB 持ち続けるため
- Android の質問は `:organize` で動かし、整理とは同時に動かさない。整理の間の質問は `busy`、手動の整理は動いている質問を止めてから始める
- 質問と答えは保存しない。履歴の画面もない
- 手動の整理に止められた質問は、Android も iOS も `busy` で返す。利用者が止めた質問は `ask-cancelled` で reject する

- iOS の整理は聞き取りと同じプロセスで動くので、定期の実行は聞き取りを止めている間だけにした。LLM が落ちると聞き取りも巻き込むため
- iOS の音声のセッションは playAndRecord、measurement、mixWithOthers にした。ほかのアプリの音楽を止めない
- iOS のシミュレーター向けは arm64 だけにした。LiteRT-LM に x86_64 のスライスがないため

- 聞き取りのマイクは 1 秒ずつ読む。VAD を飛ばす大きさは -55 dBFS。どちらも Pixel の記録で見直す
- 動作の記録は DB ではなくファイルに残す。必要な期間だけの一時的な記録で、スキーマを増やさないため
- 動作の記録は止めなくても 7 日で止まり、端末の状態は 5 分ごとに取る
- 手動の整理は dataSync の Foreground Service で動かす。`specialUse` なら時間制限はないが、新しい権限が要る
- 自分の声の更新は既定で有効にする。類似度を上げる幅は最大 0.05
- 読み込み中に止めるときは、5 秒待って `:organize` のプロセスごと終える

- アプリ ID は `dev.ambientmemo.app` で確定(利用者の判断)
- push、PR の作成、CI が通った後のマージ、Release のワークフローの実行は確認なしで行う(利用者の指示)。手順は `CLAUDE.md` の「開発の流れ」

- 画面の結合テストは Jest(jest-expo)で動かす。React Native を Vitest で読み込むのが難しいため。ほかの JS のテストは Vitest のまま
- `EngineClient` は変えず、聞き取りの操作は `TranscriptEngineClient` に分けた。`modules/engine-bridge` が実装したら `apps/mobile/src/engine.ts` で差し替える

- `first-goal` を PR 2 と PR 3 の統合ブランチにして、後続の作業をこの上に積む
- 画面のテストのタイムアウトを 30 秒に延ばした。CI の初回の読み込みが既定の 5 秒を超えたため
- `SpeakerEmbedder` はポートと Fake だけで、パイプラインからはまだ呼ばない
- スキーマ版 1 に話者の列は入れない。話者識別を作るときに足す
- `CaptureConfig` の既定値は仮(発話の上限 30 秒、待ちの上限 120 秒など)

- LLM は Gemma 4 E4B を LiteRT-LM の GPU で動かす構成を仮の第一候補にする。次善は E2B。検索は EmbeddingGemma 2 Text 270M
- LiteRT-LM の制約デコードは E4B で全件が空の出力だったので使わず、自由形式の JSON を解析する
- thinking は話者名の推定にだけ使う
- LiteRT-LM は検証の 0.19.0 ではなく 0.16.1 にした。0.17 以降が Kotlin 2.4 を要求すると pom から判断したため。品質の評価をやり直す
- モデルの通信先に `huggingface.co` と `*.hf.co` を足した。Gemma の取得に要るため。https、固定リビジョン、SHA-256 検証を条件にする
- 整理は 6 時間ごと、充電中かつ idle で、別プロセス `:organize` で動かす。失敗 3 回で飛ばすなどの値は仮

- VAD は `silero_vad.onnx`(しきい値 0.5)、ASR は `sherpa-onnx-zipformer-ja-reazonspeech-2024-08-01` の int8、話者は CAM++ advanced を仮の第一候補にする。ReazonSpeech の扱いは下の確認事項に残し、次点は `sensevoice-2024`
- 日本語のストリーミングは使わず、発話区間ごとに処理する。CER が第一候補のほぼ 2 倍だったため
- 区間の前後に実音声と無音を 0.3 秒ずつ足す。実音声の分はメモリのリングバッファに持つ
- 話者のしきい値はコサイン類似度 0.6 から始め、端末で自分の声に合わせて調整する
- `adapters` は JVM 用と Android 用に分け、同じ契約テストを流す。sherpa-onnx の jar と AAR の API が違うため

- 話者は 1.5 秒の窓を 0.75 秒ずつずらして判定し、0.60 で自分に入り 0.55 未満で出る。不明の帯は 0.45〜0.60。合成会話で誤受入 31.1% が 0.3% に下がった。Mac の embedding の計算量は約 2 倍
- 1 つの ASR 区間で話者が変わったら、文字をトークン時刻で分け、`utterance` を複数行にする。1 行 1 話者を保ち、スキーマを変えないため
- 自分を登録する前は話者を判定せず、発話は「不明」にする
- 話者のしきい値は `selfThreshold`、`provisionalThreshold` とも 0.6。2.5 秒より短い区間は仮の話者を作らない
- 登録は 3 秒以上の区間を 3 つ使った単純平均。登録し直す画面と、手動で名前を変える画面はまだない

- モデルの取得は利用者の操作でだけ始め、Wi-Fi に限らない。通信が切れたら自動で再試行せず、「続きから取得する」を押す
- 通信先は https の `github.com` と `*.githubusercontent.com` に限る。INTERNET はモデルの確定まで Release にも残す
- 途中でやめた取得のファイルを消す操作はない。最大 700 MB ほどが次の取得まで残る

- 画面用の境界は `MemoEngineClient` に分けた
- `integration-2` を PR 7 と PR 8 の統合ブランチにして、後続の作業をこの上に積む
- 区切りの無音は VAD 側で 0.8 秒にした。語の欠落と分割が減る代わりに、保存する時刻は開始が約 0.3 秒早く、終了が約 0.8 秒遅い
- 雑音の除去は仮の規則にした。文字と数字が 1 文字なら除き、2 文字は区間が 2 秒以上なら除く。短い相づちは保存されにくい
- ASR のスレッド数は 2。モデルは最初の発話で読み込み、停止まで保持する
- PR 8 はアプリに取得処理を持たず、Release の INTERNET も外していた。「モデルの確定までアプリが取得する」という方針と違い、スマホだけでは動かせないので、アプリ内の取得を足して INTERNET は確定まで残す

- 整理ジョブの既定値は仮(無音 5 分か 1,800 字で分割、再試行 1 回)。1,800 字が E4B の文脈長に収まるかは未確認
- 話題の切れ目は番号のカンマ区切りで答えさせ、JSON にしない。読めなければ再試行せず、まとまり全体を1つの話題にする。依頼の回数を増やさないため
- 話者識別ができるまで、文字起こしは話者ラベルなしで LLM に渡す。検証はラベルつきで測ったので、適合率と再現率はそのまま当てはまらない
- 録音できなかった時間も、メモの分割では無音として数える

## 調べること

- 質問の答えの品質を、架空の会話から作ったメモと質問の組で測る。根拠のメモの適合率と再現率、答えの正しさ
- 質問のたびの読み込みの時間を Pixel で測る。長ければ、整理の後にしばらく残すか決める
- 質問を `Process.THREAD_PRIORITY_BACKGROUND` のスレッドで動かしている。利用者が待っている間の速度を測る
- メモが増えたときの部分一致の検索の時間を測る。遅ければ FTS を入れる

- 話題の切れ目を、ASR の誤りを含む文字起こしと実際の会話で測る

- 聞き取り中に CPU がスリープしない理由を確かめる。録音の仕組みによるものなら、電池の目標か、聞き取る時間の決め方を見直す
- 会話の間の CPU のうち、話者の判定と VAD がそれぞれどれだけかを記録で分ける
- 画面を消して置いたままの、聞き取りなしの電流を測る

- E4B には Tensor G6 向けの NPU ファイルがない。Pixel の GPU での速度、メモリ、発熱を測る
- sherpa-onnx の jar と AAR は版を固定した URL から取得するだけで、SHA-256 を照合していない。Gradle の依存検証を入れるか決める
- 最初の発話でのモデル読み込みの時間を測る
- 手元の `mise run build:android:release` が Metaspace 不足で失敗したことがある。CI では通る
- `:organize` と本体が同時に DB を開く競合はロックを入れたが、再現試験はしていない
- 聞き取りと整理を同時に動かしたときの影響を実機で測る
- GPU はエミュレーターで動いていない。Pixel で速度、メモリ、発熱を測る
- `PRAGMA foreign_keys` を有効にしていないので、SQLite は外部キーを強制しない。有効にするか決める
- 話者のしきい値は 0.05 ずらすと結果が大きく動く(0.65/0.60 で SNR 15 dB の再現率 71.9%)。端末で調整する操作を作る
- 窓判定の Kotlin 実装で誤受入率を測り直す(`tools/eval`)
- 雑音の環境で差がある(PRESTO の再現率 70.1%)。実際の会話と端末のマイク、1 秒未満の相づちで測る
- `[HH:mm] 本文` と `自分:` が混ざる文字起こしでの LLM の品質を測る
- SNR 15 dB で話者の DER が 44.6% に悪化した。雑音の中の短い区間の扱いを決める
- zipformer は VAD の誤検知区間のすべてで文字を出した(平均 1.8 文字)。DB に書く前に除く方法を測る
- 実際の会話での CER を測る。JVS は読み上げなので数値はよく出る
- Pixel で sherpa-onnx の AAR を動かし、速度、メモリ、スレッド数を測る

- 実行中にマイク権限を取り消すと、通知も欠落の記録もなく止まる
- OS に音声を無音化されたことを検知できない
- 実機で、実際の声が `AudioRecord` から届くことを確かめる
- `expo install --check` が TypeScript 7 に対して 6 系を推奨している

## 確認してほしいこと

- 競合調査で出た案のうち、時間帯の予定と無音での自動停止は「聞き取りの停止は手動」の方針に関わる。見直すか決める
- ASR の第一候補は ReazonSpeech で学習している。モデルは Apache-2.0 だが、データセットには著作権法第 30 条の 4 の目的に限る条件があり、学習済みモデルの扱いは書かれていない。当面は今のモデルで進める(利用者の判断)。替える場合は `sensevoice-2024`(詳細は [検証-ASR.md](検証-ASR.md))
- 聞き取り中の通知はサイレント欄に入り、「停止」には展開が要る。重要度を上げるか決める
- 手動で止めていても、再起動のたびに通知が出る。止めていたときは出さないか決める
